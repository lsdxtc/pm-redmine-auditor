# PM Redmine Auditor

Скилл для аудита работы менеджеров проектов в системе Redmine через MCP-сервер `snowild/redmine-mcp`.

## Принцип работы

Агент подключается к Redmine через MCP, получает список доступных проектов, анализирует задачи,
журналы активности, структуру проектов и формирует оценку работы менеджера проекта с рекомендациями.

**Ключевое ограничение**: агент работает в режиме **только чтения (read-only)**.

---

## 1. Правила использования MCP

### 1.1 Разрешённые методы (READ-ONLY)

Агент МОЖЕТ использовать только эти методы для получения данных:

| Категория | Метод | Назначение |
|-----------|-------|------------|
| **Системные** | `server_info` | Информация о сервере и конфигурации |
| | `health_check` | Проверка соединения с Redmine |
| | `refresh_cache` | Обновление кэша enum-значений |
| **Задачи (чтение)** | `get_issue` | Детальная информация о задаче по ID |
| | `list_project_issues` | Список задач в проекте с фильтрацией |
| | `search_issues` | Поиск задач по ключевым словам |
| | `get_my_issues` | Задачи, назначенные текущему пользователю |
| | `get_issue_statuses` | Получение всех доступных статусов |
| | `get_trackers` | Получение всех типов задач (трекеров) |
| | `get_priorities` | Получение всех приоритетов |
| **Журналы** | `list_issue_journals` | Список всех журналов/комментариев задачи |
| | `get_journal` | Детали конкретного журнала |
| **Вложения** | `get_attachment_info` | Метаданные вложения |
| | `get_attachment_image` | Загрузка изображения для анализа |
| **Проекты** | `get_projects` | Список доступных проектов |
| | `get_time_entry_activities` | Активности для учёта времени |
| | `get_document_categories` | Категории документов |
| **Пользователи** | `search_users` | Поиск пользователей |
| | `list_users` | Список всех пользователей |
| | `get_user` | Детали конкретного пользователя |

### 1.2 ЗАПРЕЩЁННЫЕ методы (WRITE-OPERATIONS)

Агент НИ ПРИ КАКИХ ОБСТОЯТЕЛЬСТВАХ не должен использовать методы, изменяющие данные.
Ниже полный исчерпывающий список всех 6 write-инструментов (из 26 total):

| Метод | Причина запрета |
|-------|-----------------|
| `create_new_issue` | Создание задач — изменение данных |
| `update_issue_status` | Изменение статуса — модификация |
| `update_issue_content` | Редактирование заголовка/описания — модификация |
| `add_issue_note` | Добавление комментариев — изменение данных |
| `assign_issue` | Назначение исполнителя — модификация |
| `close_issue` | Закрытие задачи — изменение статуса |

> **ВАЖНО**: Если агент случайно вызовет запрещённый метод, он должен немедленно остановиться
> и сообщить пользователю о попытке несанкционированной операции. Агент не должен
> подтверждать, отклонять или инициировать какие-либо изменения в Redmine.

### 1.3 Порядок работы с MCP

1. **Начало сессии**: вызвать `health_check` для проверки соединения
2. **Получение контекста**: вызвать `get_projects` для списка проектов
3. **Сбор данных**: последовательно вызывать read-методы для сбора информации
4. **Анализ**: обработать собранные данные без обращения к MCP
5. **Формирование отчёта**: выдать результат пользователю

### 1.4 Работа с большими проектами (пагинация и лимиты)

Redmine REST API возвращает результаты постранично (обычно 25 записей на страницу).
При работе с проектами, содержащими > 100 задач:

- **list_project_issues**: используй параметры `limit` (max 100) и `offset` для постраничного получения
- **Приоритезация выборки**: если задач слишком много, анализируй репрезентативную выборку:
  - 15 последних обновлённых задач
  - 15 старейших открытых задач
  - 10 задач в статусе "В работе"
  - Все задачи с наивысшим приоритетом
- **Rate limiting**: делай паузу 0.5 секунды между запросами к API
- **Параллельные запросы**: не вызывай более 3 методов одновременно
- **Родительские и подпроектные отношения**: `list_project_issues` для родительского проекта
  может возвращать задачи его подпроектов. Перед тем как считать задачи «дублирующимися»
  между проектами, обязательно проверь поле `Project` через `get_issue`.

## 2. Топ ошибок ведения проектов по разработке ПО

При аудите проектов проверяй наличие этих типичных ошибок. Каждая ошибка имеет уровень критичности и вес в итоговой оценке.

### 2.1 Критические ошибки (вес: -15 баллов каждая)

**PM-CRIT-01**: Отсутствие структуры проекта
- Нет разбиения на этапы/версии (versions)
- Нет связи задач с версиями или milestones
- Все задачи свалены в одну кучу без категоризации
- **Не является ошибкой**: корректная иерархия «родительский проект → подпроект»

**PM-CRIT-02**: Задачи без описания или критериев приёмки
- Пустое или однословное описание задачи
- Отсутствие чётких критериев выполнения (Definition of Done)
- Невозможно понять, что является результатом задачи

**PM-CRIT-03**: Застрявшие задачи (stale issues)
- Задачи в статусе "В работе" более 7 дней без активности
- Задачи назначены на исполнителя, но не берутся в работу
- Отсутствие прогресса по критическим задачам

**PM-CRIT-04**: Нет приоритезации
- Все задачи имеют одинаковый приоритет
- Критические баги не помечены как высокий приоритет
- Нет понимания, что важно, а что можно отложить

**PM-CRIT-05**: Отсутствие учёта времени
- Ни одна задача не имеет учтённого времени
- Нет связи между оценкой (estimated hours) и фактическим временем
- Невозможно определить прогресс проекта по времени

### 2.2 Серьёзные ошибки (вес: -10 баллов каждая)

**PM-MAJ-01**: Некорректные статусы задач
- Задачи "Закрыты", но фактически не выполнены
- Задачи висят в статусе "Новая" слишком долго без реакции
- Статус не отражает реальное состояние работы

**PM-MAJ-02**: Отсутствие коммуникации в задачах
- Нет комментариев при изменении статусов
- Переписка ведётся вне Redmine (в мессенджерах)
- Журналы пустые — нет истории принятия решений

**PM-MAJ-03**: Неправильное назначение исполнителей
- Все задачи назначены на одного человека
- Задачи назначены на недоступных/уволенных сотрудников
- Нет балансировки нагрузки между членами команды

**PM-MAJ-04**: Отсутствие типов задач (трекеров)
- Не используются разные трекеры (Bug, Feature, Task, Support)
- Все задачи созданы как "Задача" без различения типа
- Невозможно отделить баги от новой функциональности

**PM-MAJ-05**: Задачи без связей
- Нет связей "блокирует/заблокирована" между задачами
- Нет родительских/дочерних отношений
- Нет понимания зависимостей в проекте

### 2.3 Умеренные ошибки (вес: -5 баллов каждая)

**PM-MIN-01**: Неполные данные в задачах
- Нет указания крайнего срока (due date) когда он нужен
- Отсутствует категория (category) или компонент
- Не заполнены кастомные поля проекта

**PM-MIN-02**: Дублирование задач
- Одинаковые или похожие задачи созданы многократно
- Нет проверки на дубликаты при создании

**PM-MIN-03**: Неактуальные данные
- Описания задач устарели и не соответствуют текущей реальности
- Назначенные исполнители уже не работают над задачей
- Версии/релизы не обновляются

**PM-MIN-04**: Плохая гигиена бэклога
- Слишком много открытых задач (>50 на одного менеджера)
- Бэклог не приоритизируется и не очищается
- Задачи висят годами без движения

### 2.4 Хорошие практики (бонусные баллы)

**PM-BONUS-01**: Регулярное обновление статусов (+5 баллов)
- Менеджер ежедневно обновляет статусы задач
- В журналах видна активная работа

**PM-BONUS-02**: Структурированный бэклог (+5 баллов)
- Чёткое разделение на этапы/версии
- Приоритизация по MoSCoW или аналогичной методологии

**PM-BONUS-03**: Прозрачность коммуникации (+5 баллов)
- Подробные комментарии к изменениям
- Задачи содержат полное описание с контекстом

**PM-BONUS-04**: Учёт времени и прогресса (+5 баллов)
- Регулярный лог времени в задачах
- Оценки близки к факту (точность планирования)

**PM-BONUS-05**: Работа с рисками (+5 баллов)
- Есть задачи-мониторинг рисков
- Проактивное выявление блокеров

## 3. Правила формирования оценки работы менеджера

### 3.1 Период проверки

Оценка формируется за **последнюю календарную неделю** (понедельник — воскресенье).

### 3.2 Масштаб оценки

Оценка ведётся **в разрезе каждого проекта** отдельно, затем формируется общая оценка.

### 3.3 Методика расчёта

```
Базовая оценка: 100 баллов
  - Критические ошибки: -15 баллов каждая (за тип, не за количество случаев)
  - Серьёзные ошибки: -10 баллов каждая (за тип, не за количество случаев)
  - Умеренные ошибки: -5 баллов каждая (за тип, не за количество случаев)
  + Бонусные баллы: +5 баллов каждый (макс. +25 за все бонусы)

Итоговая оценка = 100 + сумма штрафов + сумма бонусов
Минимум: 0, Максимум: 100
```

**Правило начисления**: каждый тип ошибки (PM-CRIT-01, PM-MAJ-02 и т.д.) штрафуется
**один раз за проект**, независимо от количества найденных случаев. Например:
- 5 застрявших задач = один штраф PM-CRIT-03 (-15 баллов)
- 10 задач без описания = один штраф PM-CRIT-02 (-15 баллов)
- 3 коммуникативных проблемы = один штраф PM-MAJ-02 (-10 баллов)

Это предотвращает чрезмерное снижение оценки при системных проблемах.

### 3.4 Шкала оценок

| Диапазон | Оценка | Интерпретация |
|----------|--------|---------------|
| 90-100 | **A (Отлично)** | Проект управляется профессионально |
| 75-89 | **B (Хорошо)** | Есть небольшие проблемы, но в целом хорошо |
| 60-74 | **C (Удовлетворительно)** | Заметные проблемы, требуется внимание |
| 40-59 | **D (Ниже среднего)** | Серьёзные проблемы, требуется вмешательство |
| 0-39 | **F (Критично)** | Проект неконтролируем, требуется немедленная помощь |

### 3.5 Что анализировать при оценке

Для каждого проекта собери и проанализируй:

1. **Список задач за неделю**: `list_project_issues` с фильтром по дате обновления
2. **Детали ключевых задач**: `get_issue` для 10-15 последних активных задач
3. **Журналы активности**: `list_issue_journals` для проверки коммуникации
4. **Структура проекта**: `get_projects` для проверки наличия версий
5. **Распределение по статусам**: статистика по открытым/закрытым/в работе
6. **Назначения**: кто на чём работает, балансировка нагрузки

### 3.6 Порядок сбора данных

```
Шаг 1: health_check — проверка соединения
Шаг 2: get_projects — список проектов
Шаг 3: Для каждого проекта:
   Шаг 3.1: list_project_issues(project_id, status_id="*", updated_on=">=YYYY-MM-DD")
   Шаг 3.2: Для каждой активной задачи:
      - get_issue(issue_id)
      - list_issue_journals(issue_id)
   Шаг 3.3: Проверка дублирования задач между проектами:
      - Сравнивай только по полю `Project` из `get_issue`
      - Не используй совпадение ID из `list_project_issues` как доказательство дубля
   Шаг 3.4: Подсчёт статистики по статусам
Шаг 4: Анализ и формирование отчёта
```

### 3.7 Итоговый отчёт по оценке

Для каждого проекта в отчёте должно быть:
- Название проекта и ID
- Дата аудита
- Найденные ошибки (с кодами PM-CRIT-XX, PM-MAJ-XX, PM-MIN-XX)
- Бонусы (с кодами PM-BONUS-XX)
- Расчёт баллов
- Итоговая оценка (A/B/C/D/F)

## 4. Формат рекомендаций менеджеру проекта

### 4.1 Структура рекомендаций

Отчёт формируется в следующей структуре:

```markdown
# Аудит проектов — [Дата]

## Обзор
- Проектов проверено: N
- Период: [дата начала] — [дата окончания]
- Общая оценка: [X/100] ([Буквенная оценка])

## Проект: [Название проекта]
### Оценка: [X/100] ([A/B/C/D/F])

#### Что делается хорошо
- [Конкретный положительный пункт с привязкой к задаче/данным]
- ...

#### Что требует улучшения
- [Конкретная ошибка с кодом PM-XXX-XX, пример и рекомендация]
- ...

#### Рекомендации
1. [Конкретное, измеримое действие]
2. ...
```

### 4.2 Принципы формулирования рекомендаций

**SMART-принцип**: каждая рекомендация должна быть:
- **S**pecific — конкретной, а не абстрактной
- **M**easurable — измеримой
- **A**chievable — достижимой
- **R**elevant — относящейся к найденной проблеме
- **T**ime-bound — с привязкой к сроку

**Пример плохой рекомендации**:
> "Нужно лучше управлять задачами"

**Пример хорошей рекомендации**:
> "Внедрите правило: каждая задача в статусе 'В работе' более 3 дней должна иметь
> комментарий с объяснением причины задержки. Начните с текущих 5 застрявших задач
> (ссылки: #123, #124, #125, #126, #127)."

### 4.3 Категории рекомендаций

| Категория | Когда применять | Примеры действий |
|-----------|----------------|------------------|
| **Немедленные** | Критические ошибки PM-CRIT | Созвон с руководством, экстренное перепланирование |
| **На этой неделе** | Серьёзные ошибки PM-MAJ | Внедрить процесс, обновить статусы, назначить ответственных |
| **В ближайший спринт** | Умеренные ошибки PM-MIN | Очистить бэклог, настроить трекеры, обновить описания |
| **Стратегические** | Системные проблемы | Внедрить DoD, настроить автоматизацию, обучение команды |

### 4.4 Баланс позитивной и конструктивной обратной связи

Соблюдай правило **3:1** — на каждую критическую замечание должно быть минимум
3 положительных наблюдения. Это поддерживает мотивацию менеджера и делает
рекомендации воспринимаемыми.

Структура обратной связи:
1. Начни с позитива — что менеджер делает хорошо
2. Укажи на проблемы с конкретными примерами из данных
3. Заверши конструктивными рекомендациями

## 5. Рабочий процесс аудита

### 5.1 Подготовка

1. Определи период аудита (последняя неделя)
2. Вызови `health_check` для проверки соединения
3. Получи список проектов через `get_projects`

### 5.2 Сбор данных по проекту

Для каждого проекта:
1. Получи список задач: `list_project_issues` с `project_id`, фильтруй по `updated_on`
2. Получи детали: `get_issue` для последних 10-15 задач
3. Получи журналы: `list_issue_journals` для каждой задачи
4. Зафиксируй статистику: статусы, назначения, приоритеты, наличие описаний

### 5.3 Анализ

1. Сопоставь собранные данные с чек-листом ошибок (см. references/checklists.md)
2. Посчитай баллы по формуле из раздела 3.3
3. Определи буквенную оценку
4. Сформулируй рекомендации

### 5.4 Формирование отчёта

1. Составь структурированный отчёт по шаблону из раздела 4.1
2. Укажи конкретные задачи и данные как доказательства
3. Дай рекомендации по SMART-принципу
4. Укажи приоритет действий

## 6. Граничные случаи

### 6.1 Нет доступных проектов
Если `get_projects` возвращает пустой список — сообщи пользователю, что у API-ключа
нет доступа к проектам, и проверка невозможна.

### 6.2 Проект без задач
Если в проекте нет задач — отметь это как PM-CRIT-01 (отсутствие структуры).
Пустой проект не может считаться активным.

### 6.3 Нет журналов активности
Если у задач нет журналов — это PM-MAJ-02 (отсутствие коммуникации).
Проверь дату создания задачи: недавно созданные (< 1 дня) задачи могут
не иметь журналов — это нормально.

### 6.4 Ограничение доступа
Если какой-то метод возвращает ошибку доступа — пропусти его и продолжи аудит
доступных данных. Укажи в отчёте, какие данные не удалось получить.

### 6.5 Большое количество задач
Если в проекте >100 задач — не анализируй все. Возьми:
- 15 последних обновлённых
- 15 старейших открытых
- 10 задач в статусе "В работе"
- Все задачи с высшим приоритетом

### 6.6 Родительские и подпроектные отношения
Redmine позволяет создавать иерархию проектов. При аудите:

1. Если два проекта имеют схожие названия и пересекающиеся задачи — не спеши
   классифицировать это как PM-CRIT-01 или PM-MIN-02.
2. Получи детали 2–3 задач через `get_issue` и проверь поле `Project`.
3. Если задачи принадлежат разным проектам (например, ID 897 и ID 867), но
   отображаются в обоих списках — это скорее всего родитель/подпроект.
4. В отчёте укажи, что структура родитель/подпроект проверена и не является дублированием.
